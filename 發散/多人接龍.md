# 多人接龍（Relay Brainwriting）

紙本 Brainwriting 的多人線上版。差別是紙本傳的是「一堆點子」，這裡傳的是**一條逐步長出來的鏈**：
使用者 → 場景 → 問題，每一層由不同的人接手。
**傳的是整張紙**——接手的人看得到這條鏈到目前為止的全部內容，就像紙本傳下去一樣，
但他看不到**其他鏈**，也沒有參與過前面那幾層是怎麼寫出來的。

##### 適合 :
- 沒有方向的討論
- 現場有 2 人以上、大家坐在一起的場合（工作坊、組會、黑客松開場）

---

## 為什麼值得做

這是整個專案裡最難被「把 prompt 寫詳細一點」取代的一塊。

ChatGPT 裡做不出來的原因很單純：**一個聊天室只有一份內容，所有人看到的永遠一樣。**
沒辦法做到「N 條鏈同時長，而且沒有人看得到全貌」。

> 你看得到手上這張紙的全部，但你**沒有參與它被寫出來的過程**，
> 也**不知道其他 N-1 張紙上發生了什麼**。
> 所以你一定會用自己的方式解讀它，然後往下蓋——這就是新東西的來源。

沒有任何一個參與者事先想得到最後長出來的鏈，主持人也不行。

---

## 現場流程

```
筆電（主持畫面）                 手機（每個參與者）
─────────────────────           ─────────────────────
顯示 QR code + join code   →    掃碼進入，輸入名字
名單陸續出現（等人到齊）          等待畫面
按「開始」                  →    第 1 輪：寫一個使用者（限時）
進度：已交 3/5                   交出後 → 等待畫面
自動進下一輪                →    第 2 輪：拿到別人的紙（看得到整張），往下寫
                                ⋮（共 N 輪，N 由人數決定，見下）
公布牆：N 條鏈並排          →    手機也可以看
接著用筆電跟 agent 討論
```

### 題目階梯：由 agent 依人數生成（已放棄）

> **已決定：輪數寫死成三輪，不依人數生成。** 不管幾個人都走同一份「使用者 → 場景 → 卡點」
> （`relay.DEFAULT_RUNGS`），人少時紙會傳回自己手上再接一層。下面是原本的構想，留著當紀錄。

原本的構想是題目**不要寫死**。輪數上限被現場人數綁住（見設計決定 2），所以人越多，同一段思考就可以切得越細：

3 個人（最短）

| 輪次 | 問題 |
| --- | --- |
| 1 | 想一個具體的使用者是誰（老師、里幹事、夜班護理師⋯⋯） |
| 2 | 這個使用者在什麼情境下會需要幫忙？ |
| 3 | 那個情境裡，他實際會卡在哪裡？ |

6 個人（同一條路，切細）

| 輪次 | 問題 |
| --- | --- |
| 1 | 想一個具體的使用者是誰 |
| 2 | 他一天裡最忙、最趕的是哪一段時間？ |
| 3 | 那段時間裡，他手上同時在處理哪幾件事？ |
| 4 | 這幾件事裡，哪一件最常出錯或最花時間？ |
| 5 | 他現在都怎麼處理那件事？用了什麼工具或土法煉鋼？ |
| 6 | 那個做法最讓人受不了的地方是什麼？ |

**一條硬規則**：每一題都是**往下深一層**，不能回頭要求修改前面已經寫下的東西。
因為接手的人看得到整張紙，很容易被引導去「修正」前一個人寫得不夠好的地方——
一旦開始往回改，N 條鏈就會全部被拉回各自作者的舒適圈，接龍就白做了。
（跟 Crazy 8s 的「不准刪除」是同一條規則。）

也因為看得到整張紙，階梯可以放心地層層相依：
第 5 題引用第 1 題的使用者是完全合理的，這正是「同一張紙」比「只看前一層」好的地方——
**只看一層的話，六層的鏈走到後面一定會飄掉**，深挖根本做不成。

**所有鏈共用同一份階梯**，不要每條鏈各生一份——公布時要能橫向比較，題目不一樣就比不了。

> 老實說：「用 agent 生題目」這件事本身 prompt 就做得到，不是護城河。
> 護城河是**階梯長度被現場人數綁死**、而且**N 條鏈同時在長、沒有人看得到全貌**——
> 這兩件事聊天室做不到。

## 關鍵設計決定

### 1. 平行傳遞，不是一條鏈輪流接（最重要的一點）

**不要**做成 A 寫完傳 B、B 寫完傳 C。那樣 B 在寫的時候 A 和 C 都在看等待畫面，
4 個人 3 輪下來每個人大概三分之二的時間在發呆，現場氣氛會死掉。

**改成每個人手上同時都有一條自己的鏈，同時往右傳。**

```
        第 1 輪          第 2 輪          第 3 輪
座位 0   鏈0 使用者   →   鏈3 場景     →   鏈2 問題
座位 1   鏈1 使用者   →   鏈0 場景     →   鏈3 問題
座位 2   鏈2 使用者   →   鏈1 場景     →   鏈0 問題
座位 3   鏈3 使用者   →   鏈2 場景     →   鏈1 問題
        （↑ 每一直行是同時發生的）
```

- 沒有人等任何人
- 「看不到其他鏈」的規則完全沒變
- 結束時拿到 **N 條完整的鏈**（4 個人就 4 條），不是只有 1 條

規則就一行：第 `r` 輪、座位 `s` 的人，拿到的是第 `(s - r) % N` 條鏈。

### 2. 人數決定階梯能切多細（已改）

> **已改：輪數固定三輪，跟人數無關。** 2 個人也走滿三輪，紙會傳回自己手上，
> 但輪替規則保證不會連續兩輪拿到同一張。下面是原本的規則。

**輪數不能超過人數**，否則有人會拿到自己寫過的鏈，接龍就破功了。所以：

```python
rounds = min(n_participants, MAX_ROUNDS)   # MAX_ROUNDS = 6
```

- **N ≥ 2 是下限**（原本是 3，後來改了）。3 個人 → 3 輪，每條鏈由 3 個不同的人完成
- **2 個人 → 2 輪，階梯縮成兩層**：使用者 →「他在什麼情況下會卡住？實際卡在哪裡？」
  第二層把場景和卡點併成一題，讓兩人的鏈也一樣落在具體的卡點上。
  不硬跑三輪，因為第三輪兩個人都會拿回自己寫過的紙
- **1 個人不能開始**——沒有人可以傳
- **上限壓在 6**，不是因為技術做不到，是因為 8 輪 × 每輪一分鐘加上換場，
  現場會拖到 10 分鐘以上，而且越後面的題目越難保持連貫
- N 大於輪數沒關係。8 個人跑 6 輪 = 8 條鏈，每條被 8 人中的 6 人碰過

所以人數對這個活動來說不只是「幾個人參加」，而是**同一段思考能被切成幾層**。
這是設計上刻意的：人越多，挖得越深，而不是只是點子變多。

### 3. 限時 + 可跳過

一定要有倒數，而且時間到要能空著往下走。
不然一個人手機沒電、或中途落跑，整間教室就凍在那裡。
（`StepSpec.timer_seconds` 已經有這個機制，直接沿用同一套。）

空著的格子後面那個人會拿到一張缺一層的紙 → 讓他自由發揮，不要卡住流程。

**倒數要隨輪次變長。** 因為傳的是整張紙，第 5 輪的人要先讀完前面四層才能動筆，
每一輪都給同樣的 60 秒，後面會不夠用：

```python
timer_seconds = BASE_WRITE_SECONDS + READ_SECONDS_PER_LAYER * round_index
# 例如 45 + 15 * round_index → 第 1 輪 45 秒、第 6 輪 120 秒
```

這是「同一張紙」的直接代價，換來的是鏈不會飄掉，值得。

### 4. 紙上有一層寫太模糊 → 標記，不要擋

接龍會放大垃圾，而且**第一層最致命**：第一個人寫「大學生」（太廣），
整條鏈從頭就沒有立足點，後面所有人只能繼續含糊下去。
中間層寫得爛還有救——接手的人看得到整張紙，可以靠前面幾層把方向補回來。

但**不要用切題審核去擋**，那會破壞節奏，而且每擋一次就是一次 LLM 等待。

改成：畫面上放一個「這個我看不懂」可以按（指向紙上任何一層，不只前一層），
照樣往下寫。被按過的格子在公布時標出來，當作討論材料——
「為什麼這句話別人接不下去」本身就值得聊。

如果要對第一層做品質把關，唯一值得花那個等待的地方也只有它：
第 1 輪可以考慮加一次快速的具體性檢查（「太廣了，講一個更具體的人」），
第 2 輪之後一律不擋。

### 5. 公布之後那一段，才是收成

Agent 在這裡的工作，是**只有 N 條鏈平行長出來才做得到**的那幾件事：

- **哪兩條鏈撞到同一個問題？**
  起點是完全不同的使用者、不同場景，最後卻收斂到同一個痛點
  → 那大概是真的痛點，不是誰想像出來的
- **哪一條鏈轉最大彎？**
  接手的人看得到整張紙，所以這不是誤讀，是他**刻意往一個沒人預期的方向接**
  → 那一手通常最有意思，而且現場可以直接問他當時在想什麼
- **哪一條鏈最平？** 每一層都順著前一層講，沒有人踩煞車或轉向
  → 這種鏈通常是集體共識，也就是集體盲點
- **哪些格子被按了「看不懂」？**

這幾件事單人 run 做不出來，因為根本不會有 N 條互相不知情的鏈可以比。

至於這些鏈接下來怎麼變成候選提案，有兩條路，見下一節。

---

## 公布之後：兩條路

跑完會得到 N 條鏈，每條都是一組「具體的使用者 + 具體的情境 + 具體的卡點」。
這些東西太好用了，不要只讓它們停在公布牆上。

### 路 A：直接彙整成候選 → 想法牆（預設）

Agent 把每條鏈整理成 1 個候選提案（`{title, description}`），落到**現有的想法牆**，
跟其他方法跑出來的候選排在一起，一起進收斂階段評分。

這條路**不是新東西**，就是接龍自己的 `finalize_spec`——每個方法都有彙整，接龍也有。
而且它不違背「不直接叫 LLM 幫我想 10 個題目」那個主張：
材料是一群人盲寫出來的真實情境，模型只是整理，跟其他九個方法的彙整一模一樣。

快、當場就有結果，適合時間只有半小時的場合。

### 路 B：把一條鏈當起點，餵進別的方法

一條鏈的最後一層就是一個**具體的問題**，而好幾個現有方法的第一步要的正是這個：

| 方法 | 第一步（`step_name`） | 問的東西 |
| --- | --- | --- |
| HMW | `raw_problem` | 你觀察到的原始問題或困擾是什麼？ |
| 逆向思考 | `subject` | 這次想圍繞的情境或對象是什麼？ |
| Crazy 8s | `problem` | 你們想解決的具體問題或挑戰是什麼？ |
| SCAMPER | （現有對象） | 要改造的東西是什麼？ |

所以做法可以非常小：**把鏈的內容當成那一步的答案填進去，從第二步開始跑。**
不用新的 agent、不用新的 prompt，只是換一個起點。

這就變成「方法之間可以接力」，而不是每個方法各跑各的：
接龍（多人、發散、產出情境）→ HMW（單人或小組、針對其中一個情境深挖解法）。

**現場注意**：4 條鏈全部拿去跑 HMW 就是 4 個 run，時間會爆。
公布後先投票挑 1～2 條再往下跑（投票那一票之後也會被收斂階段用到）。

### 沒被選中的鏈不會消失：情境庫

現場只挑得動 1～2 條，但**每一條鏈都已經寫進資料庫了**。沒被選中的那幾條不是廢料，
它們是一群真人花時間寫出來的具體情境——這是這個系統最值錢的私有資料。

跑過幾場之後，`relay_cells` 累積起來就是一個**情境庫**：一堆
（具體的人、具體的場景、具體的卡點）三元組，全部是人寫的，不是模型編的。

用途有三個，而且都不用新做東西：

| 用途 | 怎麼用 |
| --- | --- |
| 路 B 的起點 | 不限本場。上個月工作坊某條沒人選的鏈，這次拿來當 HMW 的起點 |
| 隨機刺激（Random Input） | 拿一個真人寫的具體痛點當靶，再用隨機詞去撞它、逼出解法。詳見 `Random Input.md` |

隨機刺激是 `進度.md` 裡**還沒調校**的方法，等於順手解掉——
它一直以來的破口就是「題目太模糊，隨機詞沒東西可以撞」，而情境庫給的正是具體的靶。

（混搭法要的三份清單看起來也能從情境庫供應，但那個方法的邏輯本身還要重想，先不動。）

**先不要急著開新表。** `relay_cells` 加上 `Rung.role` 已經夠查了：

```sql
-- 撈一批可以當起點的舊情境（排除本次 session）
SELECT chain_index, method_run_id,
       max(case when role = 'who'  then answer_text end) as who,
       max(case when role = 'pain' then answer_text end) as pain
FROM relay_cells JOIN ... WHERE session_id != :current
GROUP BY method_run_id, chain_index
```

等量大到查詢變慢、或需要加標籤與去重，再考慮獨立成 `Scenario` 表。

### 起點（seed）的三種來源

一個機制解掉三件事：

- 本次接龍的某一條鏈（路 B）
- 情境庫裡的舊鏈（跨 session）
- 想法牆上任何一個候選

實作見下面的「起點（seed）」。

## 實作

### 資料模型

**刻意不動 `MethodStep`。** 接龍自己開兩張表，現有九個方法一行都不用改，風險降到最低。
（`MethodStep.user_answer` 是單一欄位，本來以為要拆成一對多才能支援多人——
不用，接龍走自己的表就好。）

```python
class Participant(Base):
    __tablename__ = "participants"

    id: Mapped[int] = mapped_column(primary_key=True)
    method_run_id: Mapped[int] = mapped_column(ForeignKey("method_runs.id"))
    display_name: Mapped[str] = mapped_column(String(50))
    seat_index: Mapped[int] = mapped_column()
    """按 join 順序發，開始之後就固定不動——輪替規則整個建立在這個號碼上。"""
    joined_at: Mapped[dt.datetime] = mapped_column(default=_now)


class RelayCell(Base):
    """接龍網格裡的一格：第幾條鏈、第幾輪、誰寫的。"""

    __tablename__ = "relay_cells"

    id: Mapped[int] = mapped_column(primary_key=True)
    method_run_id: Mapped[int] = mapped_column(ForeignKey("method_runs.id"))
    chain_index: Mapped[int] = mapped_column()
    round_index: Mapped[int] = mapped_column()
    participant_id: Mapped[int] = mapped_column(ForeignKey("participants.id"))
    answer_text: Mapped[Optional[str]] = mapped_column(Text, default=None)
    """None = 限時到還沒寫。後面那個人會拿到空白。"""
    flagged_unclear: Mapped[bool] = mapped_column(default=False)
    """下一個人按了「這個我看不懂」。"""
    submitted_at: Mapped[Optional[dt.datetime]] = mapped_column(default=None)
    latency_ms: Mapped[Optional[int]] = mapped_column(default=None)
    """從題目出現到送出。卡很久的那一格通常是最用力想的那一格。"""

    # unique(method_run_id, chain_index, round_index)
```

`MethodRun` 加一個 `mode: str = "solo"`（`"solo"` / `"relay"`），join code 也放這裡。

### 輪替規則

整個活動的核心只有這兩行，後端前端共用同一套：

```python
def chain_for(seat_index: int, round_index: int, n: int) -> int:
    """第 round_index 輪，座位 seat_index 的人手上是哪一條鏈。

    鏈 c 從座位 c 開始，每輪往右傳一格（座位 +1），所以反過來就是 seat - round。
    輪數 <= n 時，同一個人拿到的鏈一定互不相同，不會拿回自己那條；
    人比輪數少時會拿回自己寫過的鏈，但不會連續兩輪拿到同一條。
    """
    return (seat_index - round_index) % n


def chain_so_far(seat_index: int, round_index: int, n: int) -> list[tuple[int, int]]:
    """這個人現在看得到的所有格子——手上這張紙的全部，但僅止於這張紙。

    傳的是整張紙，所以前面每一層都看得到；看不到的是**其他 N-1 條鏈**。
    第 1 輪回空 list（白紙）。
    """
    chain = chain_for(seat_index, round_index, n)
    return [(chain, r) for r in range(round_index)]
```

### 題目階梯的生成（已放棄，見上面「題目階梯」）

階梯生成一次，**整輪固定不變**，快照進 `MethodRun.relay_rungs`（JSON list of str）。
理由跟 `MethodStep.question_shown` / `timer_seconds` 被快照下來一樣：
活動進行到一半時，題目不該因為別的地方改了而跟著變。

```python
class Rung(BaseModel):
    question: str
    role: Literal["who", "context", "pain", "current_fix", "other"]
    """這一層在問哪一類東西。

    階梯是動態生成的，每場長度和用詞都不一樣，光看 round_index 無法知道
    「第 3 層」到底是場景還是痛點。有了 role，跨場次撈材料時才對得起來
    ——情境庫整個建立在這個欄位上。
    """


class RelayLadder(BaseModel):
    rungs: list[Rung]         # 長度 == rounds
    axis: str                 # 這條階梯的主軸，公布畫面上用得到
```

生成時餵給 agent 的東西：

- `rounds`（= `min(N, 6)`）——最重要的一個參數
- 這個 session 的 intake：技術背景、領域偏好、有沒有明確問題
  （`IdeationSession` 本來就存著，這裡剛好用得上）
- 硬規則：**每一題都是往下深一層，不准回頭要求修改前面已經寫下的內容**
  （後面的人看得到整張紙，很容易被引導去「修正」前一個人，那會毀掉接龍）
- 層層相依是好的：第 5 題引用第 1 題的使用者完全沒問題，紙上有
- 語氣規則：每題都要能在 60 秒內用一兩句話回答，不要問開放式大哉問

**生成時機——別讓全場等模型。**
CLI provider 一次 10～60 秒（見 README），按下「開始」才生成的話，
一屋子人會盯著 loading 轉半分鐘。做法是**在大廳階段就先產一版**：
人數到 3 以上就先生成，之後每次有人加入就重產（那時候大家還在輸入名字，等待是免費的）。
按「開始」時直接用手上現成的那一份。

**一定要有 fallback。** 模型掛掉、超時、或吐出長度不對的階梯，就退回寫死的預設三段
（使用者 → 場景 → 問題）。活動不能因為一個 LLM call 失敗就開不成。

### API

```
POST /method-runs/{id}/join          {display_name} → {participant_id, seat_index}
GET  /method-runs/{id}/lobby         主持畫面輪詢名單
POST /method-runs/{id}/start         凍結座位、算出 N、把整張網格的 cell 建好
GET  /method-runs/{id}/my-cell       ?participant_id= → {cell_id, round_index, prompt,
                                       chain_so_far: [{round_index, question, answer,
                                       flagged_unclear}], timer_seconds, deadline_at}
                                     ※ 只回這一條鏈，其他鏈一個字都不能漏出去
POST /relay-cells/{cell_id}          {answer_text} 或 {flagged_unclear: true}
GET  /method-runs/{id}/state         主持畫面：現在第幾輪、已交幾人、倒數剩多久
POST /method-runs/{id}/advance       進下一輪（全員交齊或時間到時自動觸發）
GET  /method-runs/{id}/chains        公布：N 條鏈的完整內容
POST /method-runs/{id}/analyze       跑對比分析 + 每條鏈生成候選提案
```

**用輪詢就好，不要碰 WebSocket。** 一個 run 幾個人而已，手機每 1~2 秒打一次 `/my-cell`
或 `/state` 完全撐得住。（真的想省流量的話，SSE 那套現成的也能接，但先不用。）

身分就 `localStorage` 存 `participant_id`，沒有帳號、沒有登入。
這是一小時的活動，不是要長期經營的服務——重新整理能接回原本的座位就夠了。

### 起點（seed）：把鏈餵進別的方法

`FrameworkAgent` 加一個欄位，宣告自己的哪一步可以被外部填答案：

```python
class FrameworkAgent:
    seed_step: str | None = None
    """哪一個 step_name 接受外部起點。None = 這個方法只能從頭開始。

    只有「第一步就是在問題目本身」的方法適用：HMW 的 raw_problem、
    逆向思考的 subject、Crazy 8s 的 problem。像痛點導向那種第一步是
    「最近有什麼事讓你覺得麻煩」的私人經驗，就不該被外部塞答案。
    """
```

`MethodRun` 加：

```python
seed_json: Mapped[Optional[dict]] = mapped_column(JSON, default=None)
# {"kind": "relay_chain" | "idea", "ref_id": 12, "text": "……"}
# kind 只是為了公布來源，真正被用到的是 text
```

建立 run 的時候，如果帶了 seed：

1. 先建 `MethodStep(step_index=0)`，把 `user_answer` 填成 seed 的文字
2. `agent_output_json` 留 `None`（這一步沒有人在現場回答，不需要切題審核）
3. `current_step_index` 直接設成 1

整條流程其餘部分完全不用改——對後面的步驟和彙整來說，
第一步就是「已經回答過了」，跟使用者自己打字的結果沒有差別。

**UI 上要讓人能改。** 一條鏈的最後一層未必剛好是 HMW 想要的句子，
所以那一步要顯示成「起點來自：接龍第 2 條鏈」+ 可編輯的文字框，
使用者確認或改寫之後再往下走。預填不等於鎖死。

### 前端

**手機頁（`/join/{code}`）** 只有四個狀態，畫面越笨越好：

1. 輸入名字
2. 等主持人開始
3. 作答：倒數 + 題目 + **手上這張紙的全部內容**（第 1 輪是白紙）+ 輸入框 + 「看不懂」
   - 前面幾層由上而下排，最新的那層在最下面、視覺上最重
   - 每一層旁邊都有「看不懂」，不是只有最後一層
4. 交出後等其他人（顯示「已交 3/5」，讓人知道還要等多久）

**筆電主持頁**：QR code + join code → 名單 → 每輪進度 → 公布牆（N 條鏈並排）。

QR 的內容在執行時才生成，不要寫死網址（見下）。

### ngrok 與現場網路

- **免費版網址每次重啟都會換**，所以 QR 一定要即時產生
- 免費版會先插一頁瀏覽器警告頁，**手機掃進去先跳一個警告畫面很破壞現場**。
  實作後發現這一頁**躲不掉**：掃 QR 是瀏覽器直接開網址，沒辦法帶自訂 header，
  `--host-header=rewrite` 也不影響它。能做的是：之後的 API 請求一律帶
  `ngrok-skip-browser-warning`（`frontend/src/api.ts`），主持畫面上提醒「按 Visit Site」，
  按過一次之後就不會再出現。真的要拿掉只能付費，或改走區網
- Vite 會擋不認得的 Host，ngrok 網域要列進 `server.allowedHosts`（已加），不需要 rewrite
- 最省事的做法是**只開一條 ngrok 指向前端**，後端走同一個 origin
  （Vite proxy，或打包後讓 FastAPI 直接 serve `dist/`）。
  開兩條隧道就要處理 CORS 和兩個會變的網址，不值得
- **如果大家在同一個 Wi-Fi，直接用區網 IP（`http://192.168.x.x:5173`）更快更穩**，
  ngrok 當作跨網路時的備案就好。教室 Wi-Fi 有時會擋裝置互連，兩條路都先試過再上場

## 分階段做

| 階段 | 內容 | 目的 |
| --- | --- | --- |
| 1 | 同網段、寫死預設三段階梯、**完全不接 agent**，只做到「公布牆」 | 先確認這個活動現場玩起來到底好不好玩 |
| 2 | ~~階梯改由 agent 依人數生成~~（不做，輪數寫死）+ 對比分析 + 路 A（彙整成候選落到想法牆） | 接回系統主線 |
| 3 | 路 B 的起點（seed）機制——一條鏈餵進 HMW / 逆向思考 | 方法之間能接力 |
| 4 | 情境庫：跨 session 撈舊鏈當起點、當隨機刺激的靶 | 資料庫開始產生複利 |
| 5 | ngrok / QR / 斷線重連 / 中途加入 | 上台前的收尾 |

**進度**：第 1 階段完成，第 5 階段的 ngrok / 區網 / QR / 重新整理接回座位也一起做了
（手機沒有網址就進不來，這段沒辦法等到最後）。中途加入維持「開始後就鎖住」。
接龍是方法目錄裡的第 11 個方法（`RelayAgent`，`mode = "relay"`），跟其他方法一樣能被推薦、
從同一個「開始發想」進去；`create_method_run` 看到 relay 就開大廳而不是第一步。
另外多做了一件文件裡沒寫的事：隧道一開整個 app 就在公網上，所以從區網或 ngrok
進來的請求只能碰手機用的 `/relay/{code}/…`，其他一律 403（`backend/app/access.py`）。

**第 1 階段沒有任何 LLM**，這是刻意的。活動本身如果不好玩，接再厲害的 agent 也救不回來；
而且不接模型就沒有等待，可以拉幾個人花十分鐘實測一輪。

## 還沒決定的

- 階梯的主軸要不要能選。現在預設是「使用者 → 場景 → 問題」，
  但同一套機制也可以跑「技術 → 對象 → 應用」（適合已經有技術、還沒有題目的團隊）。
  要讓主持人選，還是讓 agent 依 intake 自己判斷？
- `MAX_ROUNDS = 6` 是憑感覺抓的，實測過再調
- 公布時要不要標出每格是誰寫的（實名會不會讓人放不開）
- 中途有人加入怎麼辦（最簡單：開始後就鎖住，遲到的人用看的）
