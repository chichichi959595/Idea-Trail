# Crazy 8s

限時、限量、不准評論自己，快速衝出一堆解法。越後面擠出來的往往越有突破性。

### 紙本做法 :

1. 拿一張紙對折成 8 格
2. 設定 8 分鐘
3. 每分鐘寫一個主題

### 規則 :

1. 不准評論
2. 不准刪除
3. 先求數量

##### 適合 :
- 沒有方向的討論
- 已經知道要解決什麼問題，但解法想來想去都是那幾個

---

## 這個方法的機制是什麼

前面三、四個解法一定是老套的常識——那些是腦袋裡現成的安全牌。
**價值全在把安全牌用完之後**：最後兩、三個是被時間壓出來的，因為已經沒有現成答案可以拿了。

所以這個方法真正的變數不是「想得好不好」，是**節奏**。
一旦中間有任何東西讓人停下來（等待、被評價、回頭修改），安全牌就用不完，
方法就只剩下「寫幾個點子」這個空殼。

這一點決定了下面所有的設計取捨。

---

## 流程

共 7 步（`step_count = 7`，右側進度條顯示 `第 n / 7 步`）。

> 線上版只做 **6 個解法**，不是紙本的 8 個。8 題加上原本每題之間的等待，一輪拖太長；
> 6 題仍保留「前 3、4 個是安全牌，後面 2 個被逼出來」的空間，再少就失去這個方法的意義。

| 步驟 | `step_name` | 內容 | 限時 |
| --- | --- | --- | --- |
| 1 | `problem` | 你們想解決的具體問題或挑戰是什麼？**這一步不用想解法** | 無 |
| 2~7 | `solution_1` … `solution_6` | 針對**同一個問題**寫一個解法，**不呼叫模型** | 各 30 秒 |

六題的措辭是刻意升溫的，寫在 `crazy_8s.py` 的 `_SOLUTION_PROMPTS`：

```
解法 1/6：想到什麼就直接寫下來。
解法 2/6：不要回頭看剛剛寫的，這次刻意換一個完全不同的切入角度。
解法 3/6：越怪越好，先不要評論自己。
解法 4/6：過半了，如果卡住，故意想一個誇張、不可行的版本也可以。
解法 6/6：最後衝刺！通常最後擠出來的最有突破性。
```

第 4 題開始明說「可以寫不可行的」，因為那正是安全牌用完的位置——
與其讓人卡住，不如給他一個合法的出口繼續寫。

> 跟紙本的差異：紙本是每格 1 分鐘、共 8 分鐘。這裡壓到 **30 秒**，
> 因為打字比手寫快，而且線上少了「紙就在眼前、格子空著很難看」的壓力，
> 時間放長反而會讓人開始編輯自己。

## 關鍵設計決定

### 1. 第一步要被審核，後面六步不要（已實作）

問題陳述講得模糊，後面 6 個解法會全部白跑——所以 `problem` 那一步**應該**過 AI 的切題審核。

但 `solution_1~6` **不該**被審核，也不該被評論。原本系統對這些步驟做了三件事：
切題審核、寫一段 analysis、撈 1~3 個 idea_fragments。三件都跟方法牴觸：

- tutorial 對使用者說「不准評論自己」，系統卻對每個解法回一段講評，還顯示在畫面上
- `render_history` 把前面的 analysis 一起餵進後面步驟的 prompt——
  **寫第 5 個解法時，使用者正在讀 AI 對前 4 個的講評**，這是這個方法最想避免的錯定
- 切題 gate 會擋掉簡短、半成品的答案，而那正是這個方法要的東西

做法是 `StepSpec` 的 `analyze: bool = True`，六個解法步驟設 `False`，
那幾步不呼叫模型，直接記下答案就前進（`_answer_step_events`）。
原本每步做的切題審核，移到最後彙整時一次做完（見下面「彙整」）。放在 step 上而不是 method 上，
就是因為第一步和後面六步的答案應該受到不同待遇。

### 2. 限時到了不會把人直接拖走

倒數歸零時的順序（`FrameworkRunView` 的 `AnswerForm`）：

```
剩 10 秒起倒數轉成警示色
    ↓
歸零 → 輸入框鎖住（disabled）+ 紅框抖動 500ms
    ↓
出現「準備好進下一題了嗎？」確認
    ↓
使用者按確認 → 送出（force=true），框裡有什麼就送什麼
```

**不自動前進**是刻意的：時間到的瞬間人通常正在打字，直接跳題會把想法切斷，
而且會讓人下一題開始時還在想上一題。鎖住輸入框已經達成「不准再改」，
確認鍵只是讓他自己決定什麼時候翻頁。

### 3. 時間到 = 強制送出，不再過 gate

`force=true` 會在 step prompt 後面接上 `FORCE_ACCEPT_INSTRUCTION`，
叫模型一律 `is_relevant=true`、不要審核、盡力從裡面挖東西。

所以**限時到的那條路徑本來就繞過切題審核**。
會被 gate 擋下來的，是使用者在 30 秒內自己按送出的簡短答案。

### 4. 完全沒寫 = 直接跳過，不呼叫模型

`_answer_step_events` 裡：

```python
answer_text = payload.answer.strip()
if answer_text:
    ...  # 呼叫模型
else:
    # 限時到了但什麼都沒打——直接記成沒作答，不要拿一個不存在的答案去跑切題審核
    current_step.user_answer = None
    current_step.agent_output_json = None
```

空白的那一格在發想歷程裡會顯示「（時間到，這題沒有作答）」。
六格不一定要填滿，這是允許的狀態，不是錯誤。

### 5. 題目與限時在建立當下就快照

每前進一步，後端才建立下一個 `MethodStep`，並把 `question_shown` 和 `timer_seconds`
一起寫進那一列：

```python
MethodStep(
    step_index=next_index,
    step_name=agent.steps[next_index].name,
    question_shown=agent.question_for(next_index),
    timer_seconds=agent.steps[next_index].timer_seconds,
)
```

意思是：**跑到一半的 run 不會因為之後改了方法定義而變形**。
把 30 秒調成 45 秒，只影響之後開始的 run。

## 彙整：最後才判斷，一個解法一個候選

這是 Crazy 8s 跟其他方法差最多的地方，也是它擁有自己 `finalize_spec` 的原因。

共用的預設做法是「去重、合併相近的片段，彙整成 2~4 個彼此有區隔的 Project Concept」。
對 Crazy 8s 完全錯誤：它的材料是**同一個問題的 6 個解法**，
硬壓成 2~4 個互不相關的題目，等於把這個方法剛剛產出的東西毀掉。

而且「把 6 個壓成 3 個」本身就是在決定哪幾個活下來——
那是**評價**，而評價是想法牆之後收斂階段的工作，使用者在那裡有一票。
彙整這一步不該替他先砍掉五個。

```python
def finalize_spec(self, all_steps: list[MethodStep]) -> FinalizeSpec:
    written = sum(
        1 for s in all_steps if s.step_name.startswith("solution_") and s.user_answer
    )
    count = max(1, written)
    ...
    return FinalizeSpec(material, 1, count)
```

- 解法步驟沒有經過任何審核，所以彙整時**逐一判斷是不是在試著解決這個問題**：
  亂打字、空洞、完全離題的跳過；**誇張、不可行、很短都不算跳過的理由**
- **一個算數的解法 → 一個完整的專案主題**：保留原本的核心想法，補上要做什麼、給誰用、
  怎麼解決原本的問題；太誇張的收斂成做得出來的版本，但不換成別的想法
- **不合併、不因為弱而淘汰、不補充**使用者沒寫的想法
- 數量是**動態**的：`1 ~ n`，`n` = 實際寫出來的解法數。寫了 4 個卻要求 6 個，
  只會讓模型現編 2 個出來
- 下限夾 1：全部逾時的 run 沒有東西可以轉換，要求 0 個會讓空結果看起來像成功。
  夾成 1 會讓它誠實地 `status="failed"`，而 failed 是可以重跑的

### 數量要同時寫進 schema 和 prompt 文字

不是冗贅。`anthropic_api.py` 的 `_sanitize_schema` 會把 `minItems`/`maxItems`
從請求裡剝掉（structured outputs 不接受 array 長度限制），
**所以走 Anthropic 那條路線時，prompt 文字是唯一在約束數量的東西**。
兩個 CLI provider 則會照 schema 走。

### 輸出形狀不特別處理

即使材料特殊，吐出來的還是跟所有方法一樣的 `{title, description}`。
因為收斂階段要把不同方法的候選擺在一起評分比較，形狀不一樣就比不了。

實際落到 `Idea` 表時帶 `source_method="crazy_8s"`，在想法牆上有自己的標籤。

## 一輪跑下來會發生什麼

```
選方法 → 建 MethodRun（記下 provider / model / step_model）
    ↓
第 1 步：講清楚問題         → 呼叫模型（切題審核 + analysis + 碎片）
    ↓
第 2~7 步：各 30 秒衝一個解法 → 只記答案，不呼叫模型，直接下一題
    ↓
第 7 步答完 → 彙整呼叫（用 run.model）：逐一判斷 + 寫成完整專案主題
    ↓
n 個 Idea 落到想法牆，run.status = "done"
    ↓
（未來）收斂階段：人 + agent 一起評分、查競品、砍掉
```

模型角色：**每一步用 `step_model`，彙整用 `model`**。
理由是兩種呼叫難度差一個量級——步驟只是讀一段話，彙整是團隊真正帶走的東西。

彙整如果回來是空的，run 會變成 `failed` 而不是 `done`，畫面上出現「重新彙整」，
按下去只重跑最後那一步，前面六個答案不用重打。

## 已知問題

原本這裡列的四項（每個解法被 AI 講評、前面的 analysis 造成錯定、切題 gate 擋掉簡短答案、
每步阻塞呼叫摧毀節奏）都由 `analyze=False` 一次解掉：解法步驟沒有呼叫，
就沒有講評、沒有 gate、沒有錯定、也沒有等待。

## 還沒決定的

- 30 秒是不是對的。太短會變成只能寫短句，太長會開始自我編輯
- 六題的升溫措辭要不要再調（現在第 4 題給「可以寫不可行的」出口）
- 使用者中途想改前面的解法怎麼辦（紙本規則是「不准刪除」，目前系統也不給改，
  這是對的嗎？還是該允許但記錄下來）
- 六個候選全部落到想法牆，會不會把牆塞爆——這取決於收斂階段多快做出來
